# Apply Proven Fixes from Research

I have found standard, working configurations for both PostgreSQL HA (using Bitnami/Zalando images) and Redis Sentinel (using a proper healthcheck-based startup order). I will apply these proven patterns to fix your environment.

## 1. Fix Redis Sentinel (`redis/sentinel/docker-compose.yml`)
The issue is simply startup order. Sentinel containers start before the Master is ready.
-   **Action**: Add `healthcheck` to `redis-master` and update sentinels to `depends_on: service_healthy`.
-   **Config**:
    ```yaml
    redis-master:
      healthcheck:
        test: ["CMD", "redis-cli", "ping"]
        interval: 1s
        timeout: 3s
        retries: 30
    sentinel1:
      depends_on:
        redis-master:
          condition: service_healthy
    ```

## 2. Re-architect PostgreSQL HA (`postgresql/ha/docker-compose.yml`)
The current custom setup with `postgres:alpine` and `pgbouncer` is fragile because it lacks a proper failover controller (like Patroni) and relies on manual config files that clash with container entrypoints.
-   **Action**: Switch to the **Bitnami** image stack, which is industry-standard for Docker Compose. Bitnami images handle permissions and config generation automatically via environment variables.
-   **New Architecture**:
    -   **PostgreSQL**: `bitnami/postgresql-repmgr` (Built-in Replication Manager).
    -   **PgBouncer**: `bitnami/pgbouncer` (Auto-configures based on env vars, no more permission hell).
-   **Why**: This eliminates the need for `root` user, `init` containers, or manual `chmod`. It just works out of the box.
